# Esmeworld sync API (contract between the app and the sync server)

Status: **v1.2** (2026-10-28: adds section G, the Pinterest board endpoint), **v1.1 amended after security review 2026-10-28** (v1 agreed 2026-10-28). The server lives in `sync/` (Cloudflare Worker + D1). The client lives in `hub/src/sync/` (built later against this contract). Both halves must follow this file exactly. The amended parts are sections A to F below; where they differ from v1 they replace it.

## Goals and non-goals
- One person, several devices (Mac app, iPhone, browsers). Each device keeps a FULL local copy in IndexedDB and works offline; the server is the meeting point and an off-device backup.
- Free tier only. No accounts, no third-party auth: ONE shared passphrase (chosen by Esme, stored in her password manager, never printed or logged anywhere).
- Last write wins PER ROW (single user). Nothing is ever hard-deleted: "kill" is archive (`status: "archived"`), so the sync only ever upserts rows.
- Not in scope here: journal end-to-end encryption (a later plan; journal rows will arrive as opaque ciphertext strings in `data` and the server must not care), push notifications.

## Rows
Two tables are synced: `items` and `goals` (the same shapes as `hub/src/domain/types.ts`). Each synced row additionally carries `updatedAt`: integer epoch milliseconds, set by the writing device at every local change (see F for how). The primary key is `(table, id)`. The server treats `data` as an opaque JSON object.

## Authentication
- The client derives a token from the passphrase (B). It sends `Authorization: Bearer <token>` on every request except `GET /v1/health`.
- The server NEVER stores the passphrase or the token. It stores only `SYNC_TOKEN_HASH = hex(SHA-256(token))` as a Worker secret, and compares `hex(SHA-256(presentedToken))` to it in CONSTANT TIME.
- All error bodies are small JSON `{ "error": "<short code>" }` (codes in E); never echo input; never include stack traces.

### A. Rate limiting (amended)
- **Buckets.** Failed attempts are counted per bucket:
  - the client IPv4 address from `CF-Connecting-IP`;
  - for IPv6, the /64 (the first four groups of the expanded address; IPv4-mapped IPv6 addresses count as their IPv4 address);
  - one shared bucket `unknown` when the header is absent or unparseable.
- **Per-bucket limit.** At most 5 failed attempts per bucket per 15 minutes. A bucket at its limit gets `429` with `Retry-After` for EVERY request, including one with the correct token. This means a correct guess cannot be told apart from a wrong one while locked.
- **Atomic recording.** Every wrong or missing token is recorded in D1 table `auth_failures(ip, ts)` with ONE conditional insert that only succeeds while the bucket is under its limit. Old rows are pruned in the same batch. Outcomes:
  - nothing inserted: `429`;
  - inserted, and the global cap had already been reached: `429`;
  - otherwise: `401`.

  Concurrent requests therefore cannot exceed the limit, and failures keep being recorded during a global lockout.
- **Global cap.** When 100 or more failures were recorded across all buckets in the last hour, every bucket's limit drops from 5 to 1. Requests that present the correct token from a bucket under its (lowered) limit still succeed.
- Only the bucket key and a timestamp are stored; never the presented token or anything derived from it.
- **Passphrase strength.** Online guessing is bounded at a few attempts per bucket per 15 minutes, but the passphrase is the only secret. It must be long and random: at least 16 characters (the setup tool enforces this); a password-manager-generated passphrase is recommended.

### B. Token derivation (amended)
- `token = lowercase hex(PBKDF2-HMAC-SHA256(UTF-8(NFC(passphrase)), salt = "esmeworld-sync-v1", iterations = 200000, length = 32 bytes))`.
  - The passphrase is Unicode-normalized to **NFC** before encoding, so composed and decomposed accented characters derive the same token.
  - The token is 64 lowercase hex characters.
- `SYNC_TOKEN_HASH = lowercase hex(SHA-256(UTF-8(token)))`.
- The header is exactly `Authorization: Bearer <token>`: the word `Bearer`, exactly one space, the token. The server accepts any case for the word `Bearer`.
- Reference implementation: `sync/shared/token.ts` (WebCrypto only).

## Endpoints
`GET /v1/health` (no auth) -> `200 { "ok": true, "version": 1 }`.

`POST /v1/sync` (auth required, `Content-Type: application/json`):
Request:
```json
{ "deviceId": "string 8-64 chars [A-Za-z0-9_-]",
  "cursor": 0,
  "changes": [ { "table": "items" | "goals", "id": "string", "updatedAt": 1790000000000, "data": { } } ] }
```

### C. Server behaviour (amended)
All database work for one request happens inside ONE D1 batch (one transaction):

1. **Validate everything first.** This covers types, sizes and table names. `updatedAt` must be a positive safe integer no more than 24 h ahead of the server clock. Reject the whole request with `400` on any invalid change; nothing is applied. Unknown extra top-level keys are ignored.
2. **Cursor check.** If `cursor` is greater than the server's current highest seq, answer `409` (see D); nothing is applied.
3. **Apply each change by last-write-wins.**
   - If no row exists, insert it.
   - Otherwise replace the row only when `updatedAt` is greater, or equal with a lexicographically greater `deviceId` (deterministic tie-break).
   - Changes are applied in request order.
   - Every row actually written gets a new server sequence number `seq`: an increasing integer from a counter row in D1, with gaps allowed.
   - Changes not written count as `ignored`.
4. **Paged rows.** Collect rows with `seq > cursor`, ordered by `seq`, excluding the caller's own versions: a row is excluded when its `device_id` equals the caller's `deviceId` AND this request contains a change with the same `table`, `id` and `updatedAt`. Rows other devices wrote are never hidden. A page holds at most 500 rows and at most 1 MiB of `data`; it always holds at least one row if any qualify. `hasMore: true` when more remain.
5. **Returned winners.** For every `(table, id)` in this request whose stored row is NOT exactly a version this request sent (same `deviceId`, `updatedAt` AND `data`), the stored row is returned too. This is how a device learns that its change lost: to an older-clock edit, a tie-break, or its own reused timestamp. Returned winners:
   - are appended after the paged rows;
   - appear at most once per `(table, id)`, and not at all if already among the paged rows;
   - do not count toward the page limits;
   - never move the cursor.
6. **Cursor.** If `hasMore` is true: the maximum of the request `cursor` and the highest `seq` among the PAGED rows. If `hasMore` is false: the maximum of the request `cursor` and the server's current highest `seq` (everything up to it was either sent or is the caller's own version). The cursor never decreases.

Delivery is **at least once**: a row may be delivered again (for example as a returned winner, or after a retry), so applying a returned row must be idempotent.

**Replay.** Sending exactly the same request again changes nothing on the server: everything is `ignored`, there are no returned winners, and the response holds the same rows.

Response `200`:
```json
{ "cursor": 123, "applied": 3, "ignored": 1, "hasMore": false,
  "changes": [ { "table": "items", "id": "...", "updatedAt": 1790000000000, "data": { } } ] }
```

### D. Cursor ahead of the server (new)
If the request's `cursor` is greater than the server's highest `seq`, the server answers `409 { "error": "cursor_ahead" }` and applies nothing. This happens, for example, after the server database was reset or restored. The client must:
- keep its unsent changes;
- set its cursor to 0;
- sync again: its changes are re-sent and everything is pulled from scratch, with last-write-wins on both sides.

`GET /v1/export` (auth required) -> `200` JSON `{ "exportedAt": <ms>, "items": [...], "goals": [...] }`: all current rows' `data` objects, streamed. Because the status is sent before the body, an export cut off part-way still has status `200` and simply fails to parse (see F). The export is practical up to about 49,000 rows on the free plan.

### E. Limits and error codes (new)
Limits:
- Request body: at most 5 MiB (`413`).
- Changes per request: at most 2000.
- `id`: 1 to 128 UTF-16 code units, well-formed.
- One change as stored (its serialized form): at most 1,000,000 bytes (`row_too_large`).
- `updatedAt`: at most 24 h ahead of the server.
- Responses: 500 paged rows / 1 MiB of paged `data` (plus returned winners).

Error codes:

| Status | Codes |
| --- | --- |
| 400 | `bad_json`, `bad_request`, `bad_device_id`, `bad_cursor`, `bad_changes`, `bad_change`, `too_many_changes`, `row_too_large` |
| 401 | `unauthorized` |
| 404 | `not_found` |
| 405 | `method_not_allowed` (with `Allow`) |
| 400 | `bad_board` (G) |
| 409 | `cursor_ahead` |
| 413 | `payload_too_large` |
| 415 | `unsupported_media_type` |
| 429 | `rate_limited` (with `Retry-After` in seconds) |
| 500 | `server_misconfigured`, `internal` |
| 502 | `pinterest_unavailable` (G) |

Every response carries `Cache-Control: no-store`. `Retry-After` is exposed to browsers via `Access-Control-Expose-Headers: Retry-After`.

## CORS
- Allowed origins (exact match): `https://life-hub-eoy.pages.dev`, `https://*.life-hub-eoy.pages.dev` (preview deployments; one DNS label), `esmeworld://app`, `http://127.0.0.1:5173`, `http://127.0.0.1:4173`.
- Allowed methods `GET, POST, OPTIONS`; allowed headers `Authorization, Content-Type`; exposed header `Retry-After`.
- Preflight is answered `204` with `Access-Control-Max-Age: 600`. No credentials mode, never `*`.
- Requests from other origins still work server-to-server (no `Origin`), but browsers from other origins get no CORS headers.

### F. Client obligations (new)
The client (`hub/src/sync/`) must:
1. **Monotonic `updatedAt`.** Stamp every local change with `updatedAt = max(Date.now(), local.updatedAt + 1)`, where `local.updatedAt` is the row's current local value. Never reuse a timestamp for different content.
2. **Self-describing rows.** Every row's `data` includes its own `id` and `updatedAt`, so the export alone is enough to restore.
3. **Apply returned rows.** Apply every row in `changes` (paged rows and returned winners) to the local copy, unless a NEWER local pending (unsent) change exists for that row.
4. **One transaction per response.** Persist the applied rows, the new `cursor`, and the removal of the changes that were sent, in ONE IndexedDB transaction. A change edited again while the request was in flight stays pending.
5. **Follow pages.** Loop while `hasMore` is true, sending the new cursor each time.
6. **Small requests.** At most 500 changes and about 1 MB per request, even though the server accepts more; split larger uploads.
7. **Device id.** Use a random per-install `deviceId` (for example 16+ random characters from `[A-Za-z0-9_-]`), generated once and stored.
8. **On `401`.** Stop automatic syncing and ask the user for the passphrase again.
9. **On `429`.** Wait at least `Retry-After` seconds before trying again.
10. **On `409 cursor_ahead`.** Reset the cursor to 0 and sync again (D).
11. **On `400 bad_change`.** If it is caused by changes stamped far in the future (a device clock that was wrong), re-stamp those changes with the current time and retry.
12. **Nightly backup.** Parse the WHOLE export as JSON before replacing the previous backup file; keep the old file if parsing fails.

### G. Pinterest board (v1.2, new)
`GET /v1/pinterest-board?board=<user>/<board>` (auth required, same Bearer token and the same auth/rate-limit
path as `/v1/sync`; a wrong token counts as a failure, a locked bucket gets `429`).

- `board` is the only parameter, given exactly once, matching `^[A-Za-z0-9_-]{1,64}/[A-Za-z0-9_-]{1,100}$`;
  otherwise `400 { "error": "bad_board" }` and nothing is fetched. Auth is checked first.
- The server fetches ONLY `https://www.pinterest.com/<board>.rss` (GET, a `User-Agent`, no credentials,
  redirects not followed), with a 5 s timeout for the whole exchange and a 2 MB cap on the body (declared or
  actual).
- From each `<item>` it takes the `<link>` and the first `<img src>` in the (entity-escaped or CDATA)
  `<description>`. A pin is returned only when its image is an `https://i.pinimg.com/` URL and its link an
  `https://www.pinterest.com/` or `https://pinterest.com/` URL (no credentials, no port); everything else is
  dropped. `/236x/` images are rewritten to `/736x/`. Duplicate links are dropped; at most 200 pins.
- Response `200`:
  ```json
  { "board": "user/board", "fetchedAt": 1790000000000,
    "pins": [ { "img": "https://i.pinimg.com/736x/…", "link": "https://www.pinterest.com/pin/…/" } ] }
  ```
  `fetchedAt` is when the server read the feed. A board with no pins gives `"pins": []`.
- Any upstream problem (network, timeout, non-200 status, a redirect, oversized body, not an RSS feed):
  `502 { "error": "pinterest_unavailable" }`. Nothing from upstream is echoed.
- The parsed result is cached at the edge (Cache API, keyed by board) for 15 minutes; failures are never
  cached. (Community reports say the Cache API has no effect on `*.workers.dev`, unverified; if so, each call there reaches Pinterest.)
- The client keeps the last good list locally and asks again only on page open when its copy is older than
  15 minutes, or on "Refresh".

## Storage (D1)
- `rows(tbl TEXT NOT NULL, id TEXT NOT NULL, updated_at INTEGER NOT NULL, device_id TEXT NOT NULL, seq INTEGER NOT NULL, data TEXT NOT NULL, PRIMARY KEY (tbl, id))` with an index on `seq`.
- `meta(key TEXT PRIMARY KEY, value INTEGER NOT NULL)` holding the `seq` counter.
- `auth_failures(ip TEXT NOT NULL, ts INTEGER NOT NULL)` with an index on `ts` and one on `(ip, ts)`; `ip` holds the bucket key from A. Old rows are pruned on write.
- Migrations live in `sync/migrations/` and are applied with `wrangler d1 migrations apply`.

## Deployment rules (hard-won)
- The Worker is named `esmeworld-sync`, the D1 database `esmeworld-sync`.
- The repo-root `wrangler.jsonc` belongs to the LEGACY WhatsApp worker: never run wrangler with that config.
- The sync config is `sync/wrangler.jsonc`. Always run wrangler from an empty directory with `--config /absolute/path/sync/wrangler.jsonc`, or from inside `sync/` only if no parent config can be picked up. Wrangler walks UP to find a config, so prefer `--config`.
- The agent that builds the server NEVER deploys and never creates cloud resources; the controller does that with Esme present.
- `SYNC_TOKEN_HASH` is set by Esme through a local helper script that prompts for the passphrase with hidden input and pipes only the derived hash into `wrangler secret put`; nothing is printed.
