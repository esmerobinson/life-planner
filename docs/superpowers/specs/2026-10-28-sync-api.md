# Esmeworld sync API (contract between the app and the sync server)

Status: agreed 2026-10-28. The server lives in `sync/` (Cloudflare Worker + D1). The client lives in `hub/src/sync/` (built later against this contract). Both halves must follow this file exactly.

## Goals and non-goals
- One person, several devices (Mac app, iPhone, browsers). Each device keeps a FULL local copy in IndexedDB and works offline; the server is the meeting point and an off-device backup.
- Free tier only. No accounts, no third-party auth: ONE shared passphrase (chosen by Esme, stored in her password manager, never printed or logged anywhere).
- Last write wins PER ROW (single user). Nothing is ever hard-deleted: "kill" is archive (`status: "archived"`), so the sync only ever upserts rows.
- Not in scope here: journal end-to-end encryption (a later plan; journal rows will arrive as opaque ciphertext strings in `data` and the server must not care), push notifications.

## Rows
Two tables are synced: `items` and `goals` (the same shapes as `hub/src/domain/types.ts`). Each synced row additionally carries `updatedAt`: integer epoch milliseconds, set by the writing device at every local change (the client adds this field in a later task; the server treats it as required). The primary key is `(table, id)`.

## Authentication
- The client derives a token from the passphrase in the browser/app: `token = hex(PBKDF2-HMAC-SHA256(passphrase, salt = "esmeworld-sync-v1", iterations = 200000, length = 32 bytes))`.
- The client sends `Authorization: Bearer <token>` on every request except `GET /v1/health`.
- The server NEVER stores the passphrase or the token. It stores only `SYNC_TOKEN_HASH = hex(SHA-256(token))` as a Worker secret, and compares `hex(SHA-256(presentedToken))` to it in CONSTANT TIME.
- Rate limiting (D1 table `auth_failures`): after 5 failed attempts from the same client IP within 15 minutes, answer `429` with `Retry-After` to that IP (even for a correct token) until the window passes; also a global cap of 100 failures per hour across all IPs (then `429` for everyone except requests that present a correct token). Failures and the limit counters must not log the presented token.
- All error bodies are small JSON `{ "error": "<short code>" }`; never echo input; never include stack traces.

## Endpoints
`GET /v1/health` (no auth) -> `200 { "ok": true, "version": 1 }`.

`POST /v1/sync` (auth required, `Content-Type: application/json`, body at most 5 MB, at most 2000 changes per request):
Request:
```json
{ "deviceId": "string 8-64 chars [A-Za-z0-9_-]",
  "cursor": 0,
  "changes": [ { "table": "items" | "goals", "id": "string", "updatedAt": 1790000000000, "data": { } } ] }
```
Server behaviour, inside one D1 batch/transaction per request:
1. Validate everything (types, sizes, table names, `updatedAt` a positive safe integer not more than 24 h in the future; reject the whole request with `400` on any invalid change; unknown extra top-level keys ignored).
2. Apply each change by last-write-wins: if no row exists, insert; else replace only when `updatedAt` is greater, or equal with a lexicographically greater `deviceId` (deterministic tie-break). Every row actually written gets a new server sequence number `seq` (monotonic integer from a counter row in D1). Rows not written (older) are counted as `ignored`.
3. Collect every row with `seq > cursor`, EXCLUDING rows whose `device_id` equals the caller's `deviceId` ONLY when the row was written in this same request (never hide older rows another device wrote), ordered by `seq`, at most 500 rows per response (`hasMore: true` when more remain).
Response `200`:
```json
{ "cursor": 123, "applied": 3, "ignored": 1, "hasMore": false,
  "changes": [ { "table": "items", "id": "...", "updatedAt": 1790000000000, "data": { } } ] }
```
`cursor` is the highest `seq` included in `changes` (or the request cursor if none). The client stores it per device and sends it next time; a client with `cursor: 0` receives everything (paginated via `hasMore`). The sync is idempotent: replaying the same request changes nothing and returns the same rows.

`GET /v1/export` (auth required) -> `200` JSON `{ "exportedAt": <ms>, "items": [...], "goals": [...] }` (all current rows' `data` objects), used for the nightly backup file on the Mac (the response may be streamed/paginated if large; at most 50 MB).

## CORS
Allowed origins (exact match): `https://life-hub-eoy.pages.dev`, `https://*.life-hub-eoy.pages.dev` (preview deployments), `esmeworld://app`, `http://127.0.0.1:5173`, `http://127.0.0.1:4173`. Allowed methods `GET, POST, OPTIONS`; allowed headers `Authorization, Content-Type`; preflight answered `204` with `Access-Control-Max-Age: 600`; no credentials mode. Requests from other origins still work server-to-server (no `Origin`), but browsers from other origins get no CORS headers.

## Storage (D1)
`rows(tbl TEXT NOT NULL, id TEXT NOT NULL, updated_at INTEGER NOT NULL, device_id TEXT NOT NULL, seq INTEGER NOT NULL, data TEXT NOT NULL, PRIMARY KEY (tbl, id))` with an index on `seq`; `meta(key TEXT PRIMARY KEY, value INTEGER NOT NULL)` holding the `seq` counter; `auth_failures(ip TEXT NOT NULL, ts INTEGER NOT NULL)` with an index on `ts` (old rows pruned on write). Migrations live in `sync/migrations/` and are applied with `wrangler d1 migrations apply`.

## Deployment rules (hard-won)
- The Worker is named `esmeworld-sync`, the D1 database `esmeworld-sync`. The repo-root `wrangler.jsonc` belongs to the LEGACY WhatsApp worker: never run wrangler with that config. The sync config is `sync/wrangler.jsonc`; always run wrangler from an empty directory with `--config /absolute/path/sync/wrangler.jsonc`, or from inside `sync/` only if no parent config can be picked up (wrangler walks UP to find one: prefer `--config`).
- The agent that builds the server NEVER deploys and never creates cloud resources; the controller does that with Esme present. `SYNC_TOKEN_HASH` is set by Esme through a local helper script that prompts for the passphrase with hidden input and pipes only the derived hash into `wrangler secret put`; nothing is printed.
